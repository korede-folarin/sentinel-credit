### Sentinel Credit — Database Design

# Purpose
The database stores the synthetic BNPL data in a structure that is auditable, query-efficient, and suitable for feature engineering. It is divided into two schemas: **raw**, which contains an immutable and faithful copy of the generator output, and **feature_store**, where model-ready features are derived.

Source data and derived features are kept strictly separate, ensuring that every feature can be traced back to an immutable raw record. This data-lineage guarantee is a core principle of the database design.

# Grain.
Each table has a clearly defined grain. The **customers** table contains one row per customer, **transactions** contains one row per BNPL order, and **repayments** contains one row per scheduled instalment.

The grain therefore reflects the natural hierarchy of BNPL lending: a customer, the orders they place, and the instalments generated by each order.


# Normalisation. 
The raw layer is largely in third normal form, with one deliberate denormalisation. Because all three tables use single-column primary keys, second normal form holds automatically.

The **repayments** table stores `customer_id` and `merchant_category` directly, even though both can be retrieved through `transaction_id`. This small redundancy avoids repeated three-table joins when aggregating repayment behaviour by customer or merchant category.

The trade-off improves feature-query performance while remaining controlled, documented, and auditable.


# Keys. 
The database retains the generator’s natural string identifiers—`customer_id`, `transaction_id`, and `repayment_id`—as primary keys, preserving direct traceability to source records.

A production system might use surrogate integer keys to improve join performance, but for a synthetic dataset where auditability is the priority, natural keys are the more appropriate choice.


# Referential integrity. 
Foreign keys preserve the relationships between the tables. Every transaction must reference a valid customer, and every repayment must reference a valid transaction.

This prevents orphaned records and ensures that each repayment can always be traced back to the order and customer it belongs to.



# Types.
Monetary values use `NUMERIC(12,2)` rather than floating-point types, ensuring pounds and pence remain exact. Dates are stored as `DATE` to support reliable time-based analysis and forecasting.

Database constraints also restrict flags to `0` or `1`, probabilities to values between `0` and `1`, and fields such as age and credit score to plausible ranges. Invalid records are therefore rejected at ingestion rather than discovered later in the pipeline.


# Indexing. 
Foreign-key columns are indexed because feature construction repeatedly joins transactions and repayments back to customers. These indexes give the database a faster way to locate related records as the tables grow, reducing the need for repeated full-table scans.

The indexes therefore reflect the project’s main query patterns rather than being added by default.


# Label and leakage handling. 
`default_flag` in the **repayments** table is the model target. The generator also produces `default_probability` and `merchant_risk_multiplier`, which influence how synthetic defaults are created.

These fields remain in the raw layer for audit and validation, such as checking whether model predictions align sensibly with the generator’s underlying risk patterns. However, they are excluded from the feature store and cannot enter the model through the approved feature pipeline.

This controls leakage at the feature boundary, where modelling inputs are defined, while preserving the original generator output for traceability.
